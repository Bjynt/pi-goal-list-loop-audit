1. pi-goal-x — the one I'd try first

This surprised me a little. It isn't the most downloaded, but its completion path is considerably harder to fool than a basic “agent says done → stop” loop.

It creates a separate completion-auditor session, explicitly strips extensions, skills, prompts and agent files by default, and treats the executor's completion message as untrusted. The auditor prompt even escapes XML-like delimiters before embedding model-controlled text, which is exactly the sort of boring defensive detail I like seeing in agent orchestration code. 
GitHub
+1

The test tree is substantial, with dedicated E2E, integration and shell suites plus tests around auditing, accounting and runtime behavior. 
GitHub

The main caveat: “read-only auditor” is partly a policy guarantee rather than a hard sandbox. The auditor receives bash alongside read/grep/find/ls and is instructed not to mutate anything. That's much better than letting the executor rubber-stamp itself, but it isn't OS-level immutability. 
GitHub

It's also being actively shipped: 0.26.1 was published August 8, 2026. 
Pi

Best for: a general-purpose /goal that you actually intend to trust unattended.

2. @narumitw/pi-goal — safest boring choice

This is probably what I'd recommend to someone who says, “I don't want the fanciest thing; I want something unlikely to ruin my Pi session.”

The architecture starts extremely cleanly: the main goal.ts is only 49 lines and composes separate command, lifecycle, run-protocol, runtime and tool modules rather than implementing everything in the extension entry point. 
GitHub

More importantly, the tests aren't superficial. There are dedicated suites for budget lifecycle, continuation, contracts, error lifecycle, factory isolation, queues, run protocol, safety, tool policy and transitions. 
GitHub

It also has by far one of the largest installed footprints here—about 28.2K monthly downloads—and 0.49.6 was published August 7. 
Pi

Why isn't it #1? Its model is fundamentally closer to well-engineered self-completion. It has explicit goal_complete and strict goal_blocked mechanics, but it doesn't give me quite the same verifier/executor separation as pi-goal-x. 
Pi

Best for: everyday autonomous Pi use where stability and lifecycle behavior matter more than adversarial verification.

3. pi-goal-list-loop-audit — strongest machinery, biggest monster

On capabilities alone, GLLA is #1.

Its completion model is excellent: executor proposes completion, a detached extension-less auditor checks it, and its regression_shield requires raw command output for verification-contract items, enforced by the orchestrator rather than simply trusting prose from the executor. It also pauses rather than treating auditor infrastructure failure as approval. 
Pi
+1

It has thoughtful handling of nasty Pi lifecycle problems too. For example, session replacement explicitly stops session-owned timers and avoids retaining stale ctx/pi handles. 
Pi

And adoption is huge: roughly 28.5K/month, basically neck-and-neck with Narumi. 
Pi

But then I opened the implementation.

The current extensions/loops/goal.ts is 10,967 lines. 
GitHub

That's the reason I wouldn't put it #1 overall. Long-running autonomous extensions are exactly where timer ownership, continuation races, stale sessions and mutable state become dangerous. Putting that much orchestration into one source file dramatically raises the cognitive cost of proving changes safe.

It's also evolving extremely quickly: pi.dev was showing 0.34.80, while the repository's current package manifest is already 0.34.103. 
Pi
+1

4. pi-codex-goal — probably my favorite codebase for the basic problem

If the goal is simply “give Pi Codex-like persistent goals and don't overengineer it,” this is excellent.

It stores state in Pi's own session custom entries, meaning goals naturally follow resume, fork, tree navigation, reload and compaction instead of maintaining a parallel database. That's a very good architectural choice. 
Pi

The tests attack the places goal loops tend to break: compaction continuation/ownership, continuation behavior, state transitions, and so forth. 
GitHub

It also has unusually serious release testing: Pi 0.84.0+, Node 24, package/install smoke tests and model-backed platform checks across macOS, Ubuntu and Windows are documented. 
Pi

Its downside is basically the inverse of GLLA: beautiful plumbing, weaker independent completion guarantees.

Best for: minimalism. If independent auditor semantics aren't essential, I'd strongly consider installing this instead of the larger systems.

1. pi-goal-list-loop-audit — strongest actual completion gate

After reading the auditor implementation, GLLA wins for unattended goal completion.

Its auditor distinguishes three things that a lot of agent loops incorrectly collapse together:

actual approval/rejection,

auditor infrastructure failure,

inability to produce a valid verdict.

An empty response or missing verdict becomes an error, not a rejection and definitely not an accidental approval. 
GitHub

More importantly, an <approved/> isn't sufficient. The code checks that the auditor actually invoked an inspection tool. If it approves without reading anything, GLLA converts that result to a disapproval. Then, when a verification contract exists, a separate orchestrator-side regression shield checks whether the auditor supplied the required raw evidence. So the verifier itself can't simply say “looks good.” 
GitHub

The lifecycle engineering is also better than I expected. It has both inactivity and wall-clock watchdogs, aborts wedged auditor sessions, detects stream/provider errors, removes event listeners, and explicitly disposes the auditor session afterward. 
GitHub
+1

And unlike pi-goal-x, the auditor has compaction enabled. The code comments correctly note that because the regression shield sits outside the auditor, degraded auditor memory can cause rejection but shouldn't manufacture the evidence necessary for approval. 
GitHub

The big negative is real, though: extensions/loops/goal.ts is currently 11,266 lines / 10,935 LOC / 590 KB. My earlier concern about that file was actually correct. There are supporting modules around it, but this central orchestrator is still enormous. 
GitHub

So:

Best verification architecture, worst maintainability among the leaders.

For a loop I'm going to leave running unattended for a long time, I'd currently choose this one.

2. pi-goal-x — probably the best-designed compromise

This is the one I'd rather maintain or extend.

Its implementation is split into dedicated modules for completion, auditor selection/execution, state, ledger, compaction, policy, storage, task handling, runtime, accounting, etc., instead of putting virtually the entire state machine in one giant driver.

I especially like the verdict parser. It only treats the final non-empty line as the approval marker. That prevents prose such as “I would output <approved/> if…” from accidentally passing the goal. 
GitHub

Its completion handling also gets an important thing right: auditor failure or rejection does not close the goal. The active goal stays open, the failure is recorded, and the executor can continue working. 
GitHub

There are two meaningful weaknesses I found in the actual code.

First, its auditor uses:

read, grep, find, ls, bash

and the “don't modify things” property is primarily enforced through auditor instructions rather than a hard process sandbox.

Second, compaction is explicitly disabled for its isolated auditor, and I couldn't find a watchdog/timeout around session.prompt(). The external AbortSignal works when the user aborts, but the implementation itself doesn't appear to have GLLA's inactivity/wall-clock protection. 
GitHub
+2
GitHub
+2

That matters during a large audit.

So I'd characterize it as:

Much cleaner architecture than GLLA, slightly weaker verifier runtime.

For normal daily use, I might actually prefer this over #1.

3. @narumitw/pi-goal — best state-machine engineering

This one impressed me most purely as conventional TypeScript engineering.

The extension entry point is tiny and composes separate runtime, command and run controllers. The complexity isn't hidden in a giant registration function.

The detail that sold me is its transition/race handling. For terminal run events, it deliberately defers publication with queueMicrotask() so listeners can't start new work and then have that work overwritten by cleanup belonging to the previous transition. It also captures a generation and refuses to emit if that generation is stale. 
GitHub

That is exactly the type of subtle bug long-running Pi extensions accumulate.

Its runtime also models distinct terminal/interruption causes instead of a generic “stopped” boolean: budget exhaustion, safety pause, retry exhaustion, unavailable tools, blocker reporting, activation rollback, etc. It persists state and invalidates stale continuation/work on state changes.

Why #3 rather than #1?

Because it is stronger at running a goal correctly than independently proving that the goal is complete. There isn't the same executor-versus-auditor trust boundary that GLLA and goal-x have.

If your priority is:

“Never get my Pi session into a weird race or corrupt continuation state”

I'd actually rank Narumi #1.

If the priority is:

“Don't let the model falsely declare victory”

it's #3.

4. pi-codex-goal — cleanest minimal implementation

This might have the nicest continuation code of all of them.

Before scheduling another turn it checks:

stale queued-work guard,

exact active goal ID,

whether that goal already has a continuation queued,

recovery state,

whether Pi is idle,

whether messages are pending.

Then it checks the goal ID again immediately before sending the continuation. 
GitHub

For post-compaction continuation it additionally captures both the current turn index and an agent-run sequence and rejects the callback if either changed. That's excellent stale-callback hygiene. 
GitHub

The continuation itself is sent as a hidden Pi follow-up using normal session mechanisms rather than some side-channel driver. 
GitHub

Persistence is similarly boring in the good sense: custom Pi session entries, clone-on-boundary semantics, equality checks to avoid unnecessary writes, compact runtime-usage entries, explicit clear tombstones. 
GitHub

Its weakness is simply that it solves a narrower problem. There isn't a heavyweight independent verifier.

If I wanted a lightweight goal loop that feels native to Pi, this is the one I'd install.

5. @misunders2d/pi-goal — more interesting than I initially gave it credit for

This implementation has one feature most of the others don't approach nearly as rigorously: capability/authority enforcement.

Its Bash handling isn't merely “tell the model not to do bad commands.” It parses commands, rejects shell metacharacter constructions, protects sensitive paths, checks workspace/symlink boundaries, classifies risky commands, makes package installation/network access require typed authority, and limits unattended Git operations to read-oriented operations such as status/diff/show/log. 
GitHub
+1

This is particularly good:

credential-looking inputs can be rejected before forwarding;

secret/key/auth paths are excluded;

paths leaving approved workspace roots are blocked;

risky Bash commands need matching explicit authority;

destructive operations can be classified separately. 
GitHub

It also protects state mutations with a goal ID + generation check, so stale model calls cannot mutate a newer goal. 
GitHub

That's thoughtful security engineering.

Why not higher? The main index.ts is still large and fairly centralized, and I haven't found completion machinery quite as elegant as GLLA's separate regression shield or runtime machinery as clean as Codex/Narumi.

But if you're worried about an unattended goal loop doing something outside its intended scope, I'd move this near the top of the shortlist.

6. pi-dgoal — extremely ambitious, but another orchestration giant

The architecture concept is strong.

It deliberately separates:

lightweight Task Plans with no auditor,

Phase Plans with a final goal audit,

Goal Plans with both per-phase and final audits. 
GitHub

The source tree has explicit boundaries for pure work-list data, runtime, goal runtime, isolated Pi processes, audit parsing/storage, startup and TUI. The project docs describe late auditor results being rejected based on session generation + goal ID + relevant revision, while technical auditor exhaustion pauses the plan rather than silently accepting completion. 
GitHub
+1

That's good.

But then src/runtime/index.ts is 6,471 lines / 5,994 LOC / 337 KB. 
GitHub

For an orchestration layer dealing with persistence, audits, continuation, TUI, commands and nine tools, that's a lot of mutable behavior concentrated into one compilation unit.

The design is arguably more sophisticated than pi-goal-x, but I trust code I can locally reason about more than code with more mechanisms.

Hence #6.

7. pi-until-done — nicest-looking code with the most important logic bug/design choice

This was the biggest change from actually reading the implementation.

I really like this repository structurally. State is event-sourced through Pi custom entries, with a schema version and replay/migration path. 
GitHub

But look at its completion flow:

decideJudge() can return:

verdict: "unavailable"

when no judge is available.

Then executeComplete() does this conceptually:

if verdict === "continue":
    reject completion

otherwise:
    completeWithApproval(...)

That means unavailable falls through to completion. 
GitHub

And from the surrounding judge code I inspected, parse/infrastructure-type failures follow the same general fail-open philosophy rather than requiring a positive done/approved verdict.

For an extension literally called until-done, I don't like that invariant.

The safe structure is:

if verdict === APPROVED:
    complete
else:
    remain active / pause

not:

if verdict === CONTINUE:
    remain active
else:
    complete

That's enough for me to drop it below the others despite arguably having the nicest small-module discipline.

So which would I actually use?

There are really three winners:

For serious autonomous coding: pi-goal-list-loop-audit.

Its auditor gate is the hardest of these to fool, and the watchdog + infrastructure/error distinction + independent regression shield are meaningful engineering, not README fluff. I'd accept the ugly 11k-line orchestrator because the completion path itself is unusually defensive. 
GitHub
+1

For the best overall tradeoff: pi-goal-x.

It gets most of the independent-audit benefits while having a codebase I'd be dramatically happier modifying. I'd love to see it copy GLLA's auditor watchdog and compaction strategy.

For clean/simple Pi-native behavior: pi-codex-goal.

Its persistence and continuation logic is excellent. If independent auditing turns out to cost more tokens/time than it's worth, this is probably where I'd end up.

And one correction to my previous answer: I was too positive on pi-until-done. Reading executeComplete() changes my view significantly because its judge failure behavior is fail-open. 
GitHub
