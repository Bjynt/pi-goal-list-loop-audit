1. pi-goal-x — the one I'd try first

This surprised me a little. It isn't the most downloaded, but its completion path is considerably harder to fool than a basic “agent says done → stop” loop.

It creates a separate completion-auditor session, explicitly strips extensions, skills, prompts and agent files by default, and treats the executor's completion message as untrusted. The auditor prompt even escapes XML-like delimiters before embedding model-controlled text, which is exactly the sort of boring defensive detail I like seeing in agent orchestration code. 
GitHub
+1

The test tree is substantial, with dedicated E2E, integration and shell suites plus tests around auditing, accounting and runtime behavior. 
GitHub

The main caveat: “read-only auditor” is partly a policy guarantee rather than a hard sandbox. The auditor receives bash alongside read/grep/find/ls and is instructed not to mutate anything. That's much better than letting the executor rubber-stamp itself, but it isn't OS-level immutability. 
GitHub

It's also being actively shipped: 0.26.1 was published August 8, 2026. 
Pi

Best for: a general-purpose /goal that you actually intend to trust unattended.

2. @narumitw/pi-goal — safest boring choice

This is probably what I'd recommend to someone who says, “I don't want the fanciest thing; I want something unlikely to ruin my Pi session.”

The architecture starts extremely cleanly: the main goal.ts is only 49 lines and composes separate command, lifecycle, run-protocol, runtime and tool modules rather than implementing everything in the extension entry point. 
GitHub

More importantly, the tests aren't superficial. There are dedicated suites for budget lifecycle, continuation, contracts, error lifecycle, factory isolation, queues, run protocol, safety, tool policy and transitions. 
GitHub

It also has by far one of the largest installed footprints here—about 28.2K monthly downloads—and 0.49.6 was published August 7. 
Pi

Why isn't it #1? Its model is fundamentally closer to well-engineered self-completion. It has explicit goal_complete and strict goal_blocked mechanics, but it doesn't give me quite the same verifier/executor separation as pi-goal-x. 
Pi

Best for: everyday autonomous Pi use where stability and lifecycle behavior matter more than adversarial verification.

3. pi-goal-list-loop-audit — strongest machinery, biggest monster

On capabilities alone, GLLA is #1.

Its completion model is excellent: executor proposes completion, a detached extension-less auditor checks it, and its regression_shield requires raw command output for verification-contract items, enforced by the orchestrator rather than simply trusting prose from the executor. It also pauses rather than treating auditor infrastructure failure as approval. 
Pi
+1

It has thoughtful handling of nasty Pi lifecycle problems too. For example, session replacement explicitly stops session-owned timers and avoids retaining stale ctx/pi handles. 
Pi

And adoption is huge: roughly 28.5K/month, basically neck-and-neck with Narumi. 
Pi

But then I opened the implementation.

The current extensions/loops/goal.ts is 10,967 lines. 
GitHub

That's the reason I wouldn't put it #1 overall. Long-running autonomous extensions are exactly where timer ownership, continuation races, stale sessions and mutable state become dangerous. Putting that much orchestration into one source file dramatically raises the cognitive cost of proving changes safe.

It's also evolving extremely quickly: pi.dev was showing 0.34.80, while the repository's current package manifest is already 0.34.103. 
Pi
+1

Best for: serious multi-hour autonomous runs where verification matters more than simplicity. I'd absolutely experiment with it, but pin versions.

4. pi-codex-goal — probably my favorite codebase for the basic problem

If the goal is simply “give Pi Codex-like persistent goals and don't overengineer it,” this is excellent.

It stores state in Pi's own session custom entries, meaning goals naturally follow resume, fork, tree navigation, reload and compaction instead of maintaining a parallel database. That's a very good architectural choice. 
Pi

The tests attack the places goal loops tend to break: compaction continuation/ownership, continuation behavior, state transitions, and so forth. 
GitHub

It also has unusually serious release testing: Pi 0.84.0+, Node 24, package/install smoke tests and model-backed platform checks across macOS, Ubuntu and Windows are documented. 
Pi

Its downside is basically the inverse of GLLA: beautiful plumbing, weaker independent completion guarantees.

Best for: minimalism. If independent auditor semantics aren't essential, I'd strongly consider installing this instead of the larger systems.

5. pi-until-done — code-quality nerd winner

This one has the architecture I most enjoyed reading about.

State is event-sourced through typed Pi custom entries; exports aren't secretly treated as the canonical database. 
GitHub

The project actually enforces structural constraints: production TypeScript must stay at ≤200 lines/file, ≤30 lines/construct, nesting ≤3, and CI runs on Linux/macOS/Windows. 
GitHub
+1

That is almost the philosophical opposite of GLLA's 10,967-line driver.

Its completion judge is mandatory and sees only the goal, criteria, verification command and cited evidence. That's a good separation. However, judge infrastructure failures fail open with a warning, which I don't love for something advertising strict verification. 
GitHub

The bigger problem today is compatibility: 0.3.1 pins its Pi peer packages exactly to 0.81.1. If you're already on Pi 0.84-era releases, that makes this much less attractive despite the excellent engineering. 
GitHub

Best for: people who care deeply about maintainable architecture and are willing to match its pinned Pi version.

My actual install shortlist

If I were setting up Pi today, I'd test three, not eight:

pi-goal-x → best overall. Strong independent auditing without GLLA's enormous central driver.

@narumitw/pi-goal → best stable/simple default. Mature, popular, well-separated code, lots of lifecycle testing.

pi-goal-list-loop-audit → best “run for hours and don't believe the executor” option. Strongest verification architecture, but I'd pin the version and treat its complexity as a real operational risk.

pi-codex-goal is the wildcard: if after using these I decided the auditors were mostly overhead, I'd probably settle on Codex Goal. It's substantially cleaner than most of the autonomous harnesses while still handling the hard persistence/continuation pieces properly.

+1
