## 0. TL;DR — should we keep checking? Do we already?

**Yes, we already do.** The user's observation about Antigravity is correct — it "doesn't wait, just keeps checking" and is fast because it never sleeps for a guessed duration. GLLA **since v0.36 (ContinuousSupervisor) already does exactly that**, and is *strictly faster* than Antigravity's pure poll because we also have an event bus.

- **Antigravity (inferred):** tight-loop `check-if-done` on durable state (ledger/file/count) with increasing backoff — poll is the only signal. In-repo description `audit/WAIT-ESTIMATION-2026-08-27.md:7`: "does not sleep for a guessed duration; it tight-loops `check-if-done` on durable state with increasing backoff. Fast when done early, still bounded when slow. No guess required." No event hook. Inferred intervals `scripts/durable-wait.mjs:nextPollMs(attempt,250,1000)` → 250→500→1000ms.
- **GLLA ContinuousSupervisor v0.38.4 (`extensions/continuous-supervision.ts`):** single checker over 7 planes `{goal,list,loop,auditor,subagent,provider-recovery,queue}`. Two inputs: (1) lifecycle `signal({plane,kind,source})` from `goal-heartbeat.ts:signalSupervisionEvent` + (2) `durableStateSignature` hash (goal policy/status/revision/pendingPhase, list objectives, loop active/iteration, recovery kind/retryAt, liveSubagentCount). **Event or durable-state change → `pollMs 0` immediate.** Missing signal → exponential fallback `SUPERVISION_MIN_POLL_MS 250` → `SUPERVISION_MAX_POLL_MS 15000` via `nextPollMs()` doubling: **250, 500, 1000, 2000, 4000, 8000, 15000ms (cap 6)** then stays 15s. Driver `extensions/goal-heartbeat.ts:signalSupervisionEvent` calls `continuousSupervisor.signal()` and `scheduleHeartbeatPoll(generation, 0)` immediate if not progress.

**Latency for a 10s task:**
- *With an event/ledger change (normal):* **0ms** — GLLA reacts immediately, Antigravity waits for next poll slice.
- *Without any event (silent completion, worst case):* GLLA worst ≤ poll slice at that moment. After a recent reset the first slices are 250/500/1000ms (median 0.5–2s); after long idle the cap is 15s → picked up ≤15s after done. Before v0.36 the `GLLA_MONITOR_INTERVAL_MS 120s` throttle would have parked daemon/monitor goals for 2 minutes — that throttle is retired (deprecated env-var only, `docs/DESIGN-long-running-supervision.md`). A 10s task now completes in ~10s, not 10s + 120s.

**Verdict:** nothing new to borrow from Antigravity's keep-checking — we already ported it (`scripts/durable-wait.mjs` + ContinuousSupervisor). If chasing the last ms, tighten `scripts/smoke.sh:wait_for_durable` cap from 1000ms to 250ms and audit the intentional settle windows (goal/list completion 2.5s eager / 15s list settle per `audit/WAIT-POLL-2026-08-27.md` 14 rows) — but never reintroduce duration guesses. See §4 table row.

## 1. Antigravity — Google's IDE/agent provider, not an npm harness

**What it is:** Google Antigravity is the IDE + provider surface for `google-antigravity` OAuth in pi (Gemini 3 via sandbox), not a standalone `pi-goal-*` extension. `npm view antigravity` → placeholder `0.0.0` by `imlucas`; `@google/antigravity` 404; `antigravity.google`/`antigravity.dev`/`developers.google.com/antigravity` → 404 or Google Sign-In wall (Closure JS); `gh api search/repositories?q=antigravity+agent` returns only skill packs (`oh-my-antigravity`, `devctx`, `GodotPrompter` — all reference the IDE by name, no harness core). `.research/` has no `src-antigravity` copy; `~/.npm-global` empty. `audit/CROSS-HARNESS-REVIEW-2026-09-01` correctly records "No package found — Gap — no actionable delta" per `AGENTS.md` scope boundary (observe/contain, not repair OS/pi core).

**Why user saw it as faster:** it never guesses a duration — it polls durable done-events with backoff and returns `{elapsedMs,checks,terminalReason}`. That is the pattern GLLA now uses for smoke (`scripts/durable-wait.mjs:estimateDurationFromHistory` median+20% headroom, 0.5×–4× clamp). The speed comes from early poll, not from a different algorithm.

**GLLA row:** supervision poll-only, increasing backoff 250→1000ms, no event bus — baseline inspiration already copied. See §0 and §4.

## 2. Codex — pi-codex-goal 0.2.0 is the "clean harness like pi with not many knobs"

**pi-codex-goal (local copy `.research/src-pi-codex-goal`):** single `ThreadGoal` stored in pi session custom entries (`CUSTOM_ENTRY_TYPE pi-codex-goal`), survives resume/fork/compaction via `GoalPersistence` coalesced `appendEntry` (`goalsEquivalent` dedup, `runtimeUsageEntry` every `RUNTIME_PERSIST_INTERVAL_MS 60s`). Controller `GoalRuntimeController` wires `runtimeState`/`persistence`/`continuation`/`status`/`recovery`. Events fan out `GoalRuntimeEvents` 13 `pi.on` hooks → `createGoalRuntimeEventHandlers` (input/context/agent/turn/session). Continuation `ContinuationScheduler.maybeContinue` at `agent_end`/`turn_end`/`session_start`: if `isIdle && !hasPendingMessages` → `pi.sendMessage({customType,content:compactContinuationPrompt,display:false},{triggerTurn:true,deliverAs:followUp})` with `<pi_goal_continuation goal_id>` marker + budget; else `scheduleContinuationCheck(id,ctx,CONTINUATION_RETRY_MS 50)` retry. Only `setTimeout` users: continuation 50ms retry + `postCompact` fallback, `providerLimitAutoResume` 5m, footer `setStatus("codex-goal")` 1Hz `setInterval` only while active. Detached `spawn` only in `clipboard.ts` (`pbcopy`/`wl-copy` 5s timeout). Tools `get/create/update_goal`, slash `/goal`. In short: **no detached auditor, no heartbeat stall, no audit-jobs churn — smooth because there's almost nothing to stall.**

**Real Codex CLI (separate binary):** Rust TUI `codex` 0.147.0 (`~/.local/bin/codex`), npm `@openai/codex` 0.152.1, `codex app-server --listen stdio://|unix://|ws://` thread daemon (threads/exec-server/daemon/remote-control). Not a pi extension — pi-codex-goal merely ports its goal UX into pi.

**Why it feels smooth:** (1) no detached worker, (2) event-only `agent_end→maybeContinue`, (3) explicit `followUp` with `continuationQueuedFor` + `passthroughContinuationInput` dedup, (4) compact prompt (`compactContinuationPrompt` — budget+guidance only) after start/resume, (5) footer 1Hz only when active — no 1778-line `goal-heartbeat.ts` wedge/zombie/subagent watchdogs. Trade-off: auditor is gone, so no independent evidence — Codex trusts the main run.

**GLLA contrast:** durable `.pi-glla/active.jsonl` + `list.jsonl` + ledger + `audit-jobs/<attemptId>/` per-auditor scratch dirs, `ContinuousSupervisor` 250ms→15s adaptive, 1778-line `goal-heartbeat.ts` (zombie/wedge/pending-latch/subagent-hang), detached `goal-auditor-worker.mjs` with 5m tool-timeout + 10m stall watchdog + hash-verified result, `goal-loop-auditor-process.ts` group kill + durable worker reaping. GLLA pays session-growth cost for evidence.

**Borrow:** compact continuation prompt for resumed work; `isIdle&&!hasPendingMessages` gate + 50ms `scheduleContinuationCheck`; session-custom-entry persistence for ephemeral goals; `onInput` passthrough dedup. **Ignore:** dropping the detached auditor entirely — offer it as an opt-in "Codex-smooth mode" (skip heartbeat wedging when `policy: goal` + no subagents + budget active) but keep `ContinuousSupervisor` for loop/list.

**Lessons:** transcript summary-resume suggests replacing GLLA's full-continuation resend (session-growth A2) with ≤160-char marker + checkpoint id (pi-goal-x pattern) — measure growth first; `/branch` preserving original mirrors GLLA archive-intent — make explicit; plan mode discipline already in `propose_goal_draft` Confirm gate — add read-only Explore phase before writes; host not stalling (no heartbeat park) reinforces A8 coalesce; parallel subagents already ahead via `pi-subagents@0.62.0` power-max + `isolation:worktree`.

**Borrow:** summary-resume/bounded marker (A2), branch-preserve semantics, plan-mode discipline, `stdio:pipe` for auditor observability (A6 from pi-dgoal, consistent with Claude stream capture). **Ignore:** transcript file format/versioning, `thread/*` host protocol, permission/hook internals — pi `ExtensionContext` cannot adopt them.
