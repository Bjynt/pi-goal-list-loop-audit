# Status-aware waiting inventory — 2026-08-27

## Decision

The first wait/poll improvement is deliberately narrow: make the smoke
harness use one absolute-deadline, durable-event poller and report why each
wait ended. Do not rewrite every runtime timer. Most GLLA runtime waits already
poll lifecycle state or have a durable callback guard; provider readiness is
not exposed through a public Pi/provider API, so a plugin cannot honestly poll
it. Fixed provider delays remain bounded retries, not claims of provider
availability.

The reusable rule is: **poll the durable done-event first, use the timer only
as a deadline, and return `elapsedMs` plus a terminal reason**. UI text remains
only for dialogs/readiness where no durable event exists. Short teardown/input
pacing sleeps are not business waits and stay unchanged.

## Implementation contract

`waitForDurableEvent` in `scripts/durable-wait.mjs` owns one monotonic,
absolute deadline. A reader is called on every poll and returns `pending`,
`done`, or a terminal reason such as `provider-failure`, `restart`, or
`aborted`. Every result includes `elapsedMs`, `checks`, and `terminalReason`.
The CLI wrapper is used by `scripts/smoke.sh` for approval and plateau waits;
UI-only waits retain literal matching and their own deadline.

## Regression contract

1. **Success before deadline:** append a matching durable event after polling
   begins; it is observed before the bound and returns `done`.
2. **Real timeout:** never append the event; the absolute deadline returns
   `timeout` rather than false success.
3. **Restart:** a first waiter ends on a persisted restart marker; a new waiter
   reads the same durable file and observes the later completion without an
   old in-memory timer.
4. **Provider failure:** a persisted recovery marker ends the wait as
   `provider-failure`, never as approval or timeout.

## Out of scope

No new provider API, Pi-core change, wholesale runtime timer rewrite, or
unbounded retry is introduced. The next task may use the recorded elapsed
samples to tune defaults, but must not turn a guessed delay into an implicit
claim that a provider is ready.
